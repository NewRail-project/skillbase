Статус: только предложение. Правила Firestore не менялись, код не писался. Нужно подтверждение владельца проекта.

## Задача 3. Очистка результатов старых Live-комнат (roomHistory)

Сейчас: `allow delete: if false` (firestore.rules, блок roomHistory), история неизменяема.
Читают: админ организации — все комнаты, преподаватель — свои (hostId).

### Минимальное правило
```
match /roomHistory/{docId} {
  // ...read/create без изменений...
  allow delete: if isStaffOf(resource.data.orgId)
    && (isAdminOf(resource.data.orgId)
        || (resource.data.hostId == request.auth.uid
            && resource.data.finishedAtMs < request.time.toMillis() - 30 * 24 * 60 * 60 * 1000));
}
```
- Админ организации удаляет любую запись своей организации; автор-ведущий — только свою и только старше 30 дней (число N — решение владельца).
- `update` остаётся запрещённым: неизменяемость содержимого сохраняется, меняется только право убрать запись целиком.
- Студенты по-прежнему не имеют доступа. Чужая организация — нет (`isStaffOf(resource.data.orgId)`).
- Облачные функции и платные сервисы не нужны.

### UI
- Страница архива/истории Live: кнопка «Удалить» у записи (подтверждение, как в delete-flows.js) — точечно.
- «Очистить всё старше N дней»: выборка своих записей (`hostId == uid`, `finishedAtMs < порог`), удаление порциями по 20–50 (writeBatch), прогресс и итог; для админа — по организации.
- Заранее показывать, сколько записей будет удалено; необратимость указать явно.

### Тесты (tools/rules-test.mjs, roomHistoryCases)
1. админ своей организации удаляет любую запись — разрешено;
2. админ другой организации — запрещено;
3. автор-ведущий удаляет свою запись старше N дней — разрешено;
4. автор-ведущий удаляет свою запись младше N дней — запрещено;
5. преподаватель удаляет чужую запись — запрещено;
6. студент и аноним — запрещено;
7. update по-прежнему запрещён (регресс).
Существующие кейсы «удаление запрещено» (строки ~2005–2044 rules-test.mjs) нужно обновить под новое правило.

### Риски
- Удаление необратимо; архив — единственная копия отчёта. Рекомендуется экспорт (JSON/Excel) перед «Очистить всё».
- Порог N считается по `finishedAtMs`, который пишет клиент ведущего; для надёжности можно сравнивать с `savedAt` (серверное время), если оно пишется через serverTimestamp.

## Задача 4. Подготовка Battle после запуска

Вывод: без изменения механики дать админу *редактируемую* подготовку после запуска нельзя.
- `battlePrepForHost()` (ui/pages/room.js) возвращает `null`, когда `room.mode === "battle"`; запуск битвы переводит комнату в этот режим и фиксирует распределение команд.
- Повторная подготовка означала бы перераспределение команд/капитанов во время битвы — это запрещено условиями (формулы, капитаны, распределение, замены не менять).
- Что можно без изменения механики: в оверлее «Экран битвы» показать *только для чтения* сводку «Состав команд и капитаны» (данные уже есть у ведущего) и кнопку «К управлению», ведущую в существующий battle-room. Это отдельная небольшая задача UI; не реализовано.
